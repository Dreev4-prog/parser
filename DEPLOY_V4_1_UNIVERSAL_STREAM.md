# DT PARSER v4.1.0 — Railway deploy

## Цель версии

Сначала добиться стабильного одиночного скана для **любой даты**, затем повторно включать multi-user load test.

## Railway topology

Оставить:

- `bot` ×1
- `fleet-worker` ×6
- `views-worker` ×1
- Redis ×1
- PostgreSQL ×1

Старые `parser-worker`, `browser-worker`, `hybrid-worker`, `stable-worker` должны быть выключены.

## Start Commands

- bot: `python bot.py`
- fleet-worker: `python fleet_worker.py`
- views-worker: `python views_worker.py`

## Обязательные общие references

`DATABASE_URL` и `REDIS_URL` должны указывать на одни и те же PostgreSQL/Redis для bot/fleet/views.

## Новые переменные

Добавлять ничего не обязательно. Defaults:

```env
BROWSER_RESULTS_WAIT_MS=4500
BROWSER_RENDER_SETTLE_MS=250
```

Они нужны только если позже захотим тюнинговать ожидание отрендеренных карточек.

## Что изменилось

1. Chromium navigation после `DOMContentLoaded` ждёт контейнер результатов и читает `page.content()` — отрендеренный DOM.
2. Один последовательный date-stream используется для любой даты.
3. Страницы с неполными датами (`unknown`) не считаются ошибкой и не вызывают partial.
4. Реальный `invalid` после page retries остаётся ошибкой.
5. Если поток достоверно пересёк выбранную дату — это завершённый скан, даже если объявлений этой даты 0.
6. Если дата глубже public page window, запускаются location shards тем же универсальным алгоритмом.
7. Cache namespace изменён на `v410:`, поэтому результаты старых 4.0.x не переиспользуются.

## Первый тест после deploy

Не начинайте сразу с пяти аккаунтов. Проверить по очереди:

1. один аккаунт → сегодня → 1 категория → 25 страниц;
2. один аккаунт → вчера → та же категория → 25 страниц;
3. один аккаунт → произвольная дата старше 2 дней → 25 страниц;
4. только если три теста завершились без partial — 5 аккаунтов одновременно.

Для чистого теста временно использовать `От просмотров: без ограничения`.
